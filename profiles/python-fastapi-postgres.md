# Optional Profile: Python + FastAPI + PostgreSQL

This profile specializes the generic protocol for FastAPI services using SQLAlchemy (sync or async) and Alembic against PostgreSQL. It is guidance, not a mandatory core dependency.

## Typical verification mapping

Use the repository's actual tooling. Common layers may include:
- Ruff (lint + format) or flake8/black;
- mypy or pyright type checking;
- pytest unit tests;
- pytest integration tests against a disposable Postgres with Alembic migrations applied (`alembic upgrade head`);
- container/image build when the service ships as an image;
- API contract checks (generated OpenAPI diff) for public APIs;
- E2E or smoke tests against a deployed preview/staging environment.

Never invent commands or disable checks when adopting this profile.

## Authentication and authorization

- Enforce authorization in dependencies or service functions used by every route, not only in the router that happens to call them today.
- Object-level authorization: loading `/items/{id}` must check that the caller may access that specific item (IDOR is the most common failure).
- Pydantic validates shape, not permission. Check that request bodies cannot set server-owned fields (`owner_id`, `role`, `tenant_id`) — use separate input and output schemas.
- Response models must exclude sensitive fields; returning an ORM object directly can leak columns.
- CORS: never combine `allow_origins=["*"]` with credentials.

## Async correctness

- Blocking calls (sync DB drivers, `requests`, heavy CPU work) inside `async def` routes block the event loop for every request. Use async clients, `def` routes (run in a threadpool), or offload.
- Do not share a SQLAlchemy `Session`/`AsyncSession` across concurrent tasks.
- Set timeouts on every outbound HTTP call.

## Data access

Pay special attention to:
- lazy-loading N+1 (relationship access in loops); use `selectinload`/`joinedload` deliberately;
- `MissingGreenlet`/implicit IO errors under async sessions — usually a lazy load outside the session;
- tenant scoping on every query;
- transaction boundaries: one unit of work per request for multi-write invariants;
- unique constraints / `ON CONFLICT` for idempotency instead of check-then-insert;
- raw SQL via `text()` must use bound parameters, never f-strings;
- pagination and `LIMIT` for plausibly large collections.

## Migration workflow

- Review autogenerated Alembic revisions by hand; autogenerate misses some changes and can emit destructive operations for renames.
- Keep `downgrade()` meaningful or state explicitly that the revision is irreversible.
- Large table changes: consider `CREATE INDEX CONCURRENTLY` (outside a transaction) and batched backfills.
- For R3 migrations, fill `templates/MIGRATION_RUNBOOK.md` and obtain human approval.

## Background work

FastAPI `BackgroundTasks` run in the same process after the response: they are lost on restart and have no retry. Use a real job system when the work must survive failures (`agents/reliability-audit.md`).

## Observability progression

Start with structured logs (request id, route, status, latency; no personal data or tokens) and error reporting. Add tracing and database metrics when scale or debugging cost justifies it.
