# AI Development System v2

Version 2 turns the v1 quality protocol into an operational system for AI-assisted engineering.

## What v2 adds

1. **Orchestration** — one coordinating agent owns scope, evidence, delegation, and final synthesis.
2. **Specialist agents** — architecture, implementation, database, security, UX, performance, reliability, regression, and shipping have explicit contracts.
3. **Risk profiles** — verification depth is proportional to impact instead of applying every check to every task.
4. **Command workflow** — reusable lifecycle commands map user intent to protocol phases.
5. **Evidence contract** — every completed material task produces a consistent verification report.
6. **Adoption model** — existing repositories can adopt the system incrementally.
7. **Stack profiles** — optional guidance may specialize the generic core without coupling it to a vendor.

## Operating model

```text
Human intent
    ↓
Orchestrator
    ├── Discovery / architecture
    ├── UX / accessibility
    ├── Database / performance
    ├── Security
    ├── Reliability / async
    └── Regression
    ↓
Consolidated plan
    ↓
Implementation
    ↓
Verification
    ↓
Quality Gate
    ↓
Human approval boundary (when applicable)
    ↓
Ship
    ↓
Post-deploy observation
```

The orchestrator may execute specialist roles itself when parallel delegation is unavailable. The contract matters more than the agent runtime.

## Risk profiles

### R0 — Trivial
Examples: typo, static copy, non-behavioral documentation.

Minimum: focused review and any cheap repository checks.

### R1 — Low
Examples: isolated visual adjustment, small internal refactor with strong test coverage.

Minimum: relevant static/type/build checks plus focused behavior validation.

### R2 — Moderate
Examples: user-facing feature, API behavior, data query change, form mutation.

Minimum: acceptance criteria, automated verification, relevant specialist gates, preview/manual validation where behavior is user-visible.

### R3 — High
Examples: auth/authorization, RLS, migrations, billing, destructive operations, cross-tenant data, critical integrations, production infrastructure.

Minimum: explicit architecture/risk review, strong automated verification, security/integrity gates, rollback or recovery consideration, human approval where required, and post-deploy validation.

Risk is determined by impact, not code size. A one-line authorization change can be R3.

## Agent output contract

Every material agent report should use this structure when applicable:

```text
Status: PASS | PASS_WITH_FINDINGS | BLOCKED | FAIL
Scope:
Observations:
Evidence:
Findings:
Files/areas reviewed:
Checks executed:
Checks not executed + reason:
Risks/assumptions:
Recommended next action:
```

A PASS cannot be based only on absence of obvious problems.

## Delegation contract

The orchestrator must:
- give specialists a bounded question;
- include relevant acceptance criteria/context;
- avoid multiple agents editing the same area concurrently unless coordinated;
- distinguish investigation from implementation;
- reconcile contradictory findings using evidence;
- own final scope and Definition of Done.

Specialists must not silently expand scope or claim global safety from a narrow audit.

## Human control

AI agents can investigate, propose, implement, test, and prepare shipping evidence. Human approval remains a hard boundary for unapproved destructive or materially production-sensitive operations defined in `AGENTS.md`.

## Vendor independence

The system describes outcomes and evidence, not a required AI vendor. It should work with coding agents capable of repository inspection and tool execution. Vendor-specific adapters belong in optional profiles, not the core protocol.
